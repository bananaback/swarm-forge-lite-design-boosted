# hotfixer

Do not edit this file. It is the shared answer template. Print this block, with your own values, at the end of your turn.

The final message of the hotfixer. The orchestrator dispatches it alone on the fast path. It ends the run itself. There is no `NEXT`. Plain text. Report references, not content: give the file path and the line number.

```
STATUS: fixed | blocked
BUG: <path:line of the failing test or the reproduction>
CAUSE: <path:line of the defect, or "unknown">
FIX: <path:line of the change>
LAYERS: <path:line, path:line ...>   (each twin that changed)
VERIFY:
- <pytest command> => exit <n>
- <run_acceptance feature> => exit <n>
- <ruff4py command> => exit <n>
RISKS: <path:line, or "none">
ASK: <only when blocked>
```

Good: `STATUS: fixed`, `BUG: tests/unit/test_config.py:22`, `CAUSE: src/config.py:31`, `FIX: src/config.py:14`, `LAYERS: src/config.py:14, tests/unit/test_config.py:22`, every `VERIFY` `=> exit 0`, `RISKS: none`.
Bad: `STATUS: fixed` with no reproduction, or the diff pasted into the message.

Write the prose fields in ASD-STE100 Simplified Technical English. Keep the field names and the tokens exact.
Keep the message thin. The diff is the record of the change. Do not restate the code.
A requirement, a scenario, or a contract change is not the work of the hotfixer. It returns `STATUS: blocked` with an `ASK` that routes the change to its owning role.
Use `blocked` only for a missing input or an owner decision that the artifacts cannot settle.
