# Design Protocol

Two protocols. The build loop (`specifier`, `coder`, `refactorer`) uses `dispatch.md`.
The requirement and design roles (`interrogator`, `modeler`, `contractor`, `critic`) use this
one. Their output is the method's own artifacts, not a build envelope: no `VERIFY`, `FILES`, or
`SUMMARY`; the proof is a **stop test**, the content is **filled forms**.

## Working state

```
design/<task>/
  BLUEPRINT.md              accepted artifact: REV n + [DRAFT|ACCEPTED]; immutable after accept
                            GOAL · CONSTRAINTS · EXCLUSIONS · REQUIREMENTS first (the interrogator),
                            then the design sections
  work/<nn>-<role>.md       the role's filled forms — its full state
  SKELETON.md               the critic's self-contained implementation contract;
                            the coder and the refactorer read this, not the blueprint
  model.json                the topology for the visual view (source of truth for the diagram)
  model.html                generated by umlview `render.py`; reload with F5
```

The interrogator also owns the **requirement document** in the repo's workplace,
`docs/specs/NN-<task>.md` — refined when a draft exists, created when none does. It is a
deliverable of the requirement gate, before the specifier runs; the blueprint stays the record of
authority if the two disagree. Never write design into the repo: only the requirement document is
authored there (`PUBLISH-DOCS.md`).

The interrogator fills `design/templates/interrogator.md` — the requirement tables — and runs
before the specifier. The design roles fill theirs and run after the specifier approves.

Each role copies `design/templates/<role>.md` to `WORK` and fills every form. `BLUEPRINT.md`
receives only the accepted projection, never raw work. A role edits its own WORK and the
blueprint sections it owns, and nothing else. The modeler writes `model.json`; the contractor
enriches it; the critic renders it with `--check`. The blueprint stays the accepted record — if
the model and the blueprint disagree, the blueprint wins and the model is regenerated.

## The visual at every gate

The operator views `design/<task>/model.html` before accepting a design section (the
interrogator has no model). The model and rules are `unclebob/uml-viewer`'s; the design team's
mapping onto it is in `<pack>/reference/model-format.md`. The viewer's only rule is the
dependency rule, so the design's DIP check is expressed by ordering `levels` core-inner →
shell-outer — not by a new finding.

## Input — the design dispatch

Same shape and conventions as `dispatch.md`: a verb-led headline, labelled blocks, and the ask
with the hard constraints **last**.

```
<Verb>: <task name> — <one-line outcome>

#TASK        <stable task name>
#ROLE        <interrogator | modeler | contractor | critic>
#WORK        design/<task>/work/<nn>-<role>.md
#BLUEPRINT   design/<task>/BLUEPRINT.md

#REQUEST     <the operator's ask, verbatim — the interrogator only>
#DRAFT       <docs/specs/NN-*.md, or none — the interrogator resolves it with the operator>
<PASTE the draft's acceptance criteria, verbatim, when a draft exists>
#ACCEPTANCE
<one observable business check per line — its source moves with the phase; see below>
#FEATURES    <approved feature paths, or none>
<PASTE the approved scenario outcome lines>
#FROZEN
<PASTE the accepted upstream sections at full text, plus the predecessor's FROZEN HANDOFF; do not reopen>

#ENV
<PASTE every ENV line from PROJECT.md, the forbidden actions included>
#CONVENTIONS
<the one non-obvious invariant the feature/IR does not state; else "none">

#ASK
<this role's one-line ask: what it must produce>
#STOP TEST
<PASTE this role's literal pass/fail from reference/design-quality.md, verbatim — never a pointer>

Output: <pack>/protocol/<role>.md — exactly that block.
If a detail is missing: `ASSUMED: <...>`, or surface it as a DECISION.
```

The headline names the domain: `Frame:` (interrogator), `Model:` (modeler), `Contract:`
(contractor), `Critique:` (critic).

**`#FROZEN` per phase.** The interrogator runs first, so it has no accepted upstream — its
`#FROZEN` is the operator's ask and the draft requirement, when one exists; the interrogator
resolves that existence with the operator rather than assuming it. Every later role receives the
accepted sections at full text, not their paths.

**`#STOP TEST` is last, and it is copied literally.** `STATE: settled` is defined by it, so it
takes the envelope's final, exact-attention slot; a pointer there spends that slot on a
filename. Copy the role's row out of `reference/design-quality.md` verbatim — it runs
131–1,310 B, and the role then needs no separate read of that file.

`ACCEPTANCE` is the bridge: the observable behavior the receiving role must provide. The
orchestrator fills it by copying, never by designing. Its source moves with the phase: for the
**interrogator** it is the existing draft's own criteria, to audit — the interrogator resolves
whether a draft exists and `none` means it derives the checks itself (and then creates the
document);
for the **specifier** it is the accepted requirement rows the feature must pin; for the
**design roles** it is one approved scenario outcome per line. If a feature states no outcome
line, the interrogator derives the check and inlines it.

A role resumed by its `sessionID` already holds this envelope: send the new evidence and the one
change, not the envelope again.

## Output — the design answer

```
TASK: <stable task name>
ROLE: <interrogator | modeler | contractor | critic>
STATE: settled | open | blocked
SPEC: <the requirement document path in the repo, REV <n> [refined | created]>   (interrogator only)
WORK: <working file path>
PRODUCED: <SECTION> REV <n> [DRAFT|ACCEPTED]        (one per line)
STOP TEST: <the literal check> -> pass | fail
DECISIONS: <n>
  D1 [<named rule>] <question> | options: <a> | <b> | <c> | answer: <operator's>
FROZEN HANDOFF: <what the next role must treat as immutable, in method vocabulary>
REVISION REQUESTS: <"[section] — reason — route to <role>" or "none">
OPEN RISKS: <design defaults and assumptions, or "none">
NEXT: <specifier | modeler | contractor | critic | coder | operator>
```

`STATE: settled` = the stop test passes and every DECISION was answered at the role's
`question` gate. `open` = a decision was surfaced, unanswered. `blocked` = a frozen fact is
missing or contradictory. Each DECISION names the rule that forces it, so the operator
decides a named craft question. The field-to-concept mapping is in
`reference/design-craft-front.md` and `reference/design-craft-design.md`.

## Crossing the boundaries

- **In (requirement):** the operator states an ambiguous ask, with a draft requirement when one
  exists. The interrogator first resolves the requirement document with the operator: a draft
  (`docs/specs/NN-<task>.md`) is read and refined, and when none exists the interrogator creates
  it. Either way the doc is a deliverable of the gate, one-to-one with the accepted record and in
  business vocabulary. It frames the ask, makes it measurable, tables its behaviour, and discharges
  what nobody stated. `REQUEST` is the ask verbatim; the draft is an input, never an authority.
  Business vocabulary is not re-encoded before handoff — Abbott's pass does the translation.
- **Across (acceptance):** the interrogator settles the record; the **specifier** inspects it as a
  second party, then derives Gherkin with one scenario per requirement. A defect routes back to
  the interrogator as a `[REVISION REQUEST]`. The record is the authority; the feature is derived
  from it, never the reverse.
- **Out (design):** the specifier approves a feature; `ACCEPTANCE` is one approved scenario outcome
  per line and the design gate opens at the modeler.
- **Out (build):** the critic settles `SKELETON` and projects it into `design/<task>/SKELETON.md`.
  The coder's build dispatch is built from that file: one method's name, its contract, and its
  responsibility sentence are the whole prompt. If the coder needs more, fix the contract — do not
  pad the prompt.

## Revision protocol

- Accepted text is immutable. A change is a `[REVISION REQUEST]` line, never an edit; the
  owning role re-runs, REV increments, the changed span is marked. No revision log is kept —
  the artifact is the record.
- Card-local change: re-run Steps 4–15 for that card and its direct collaborators.
- **Requirement-level change:** a GOAL, CONSTRAINTS, REQUIREMENTS or table change is not
  contained. Re-run the interrogator, then the specifier, then re-validate every design section
  the change reaches; do not pretend the edit was contained.
