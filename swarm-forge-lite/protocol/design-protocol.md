# Design Protocol

Two protocols. The build loop (`specifier`, `coder`, `refactorer`) uses `dispatch.md`.
The requirement and design roles (`interrogator`, `architect`, `designer`, `critic`)
use this one. Their output is the artifacts of the method, not a build envelope: no
`VERIFY`, `FILES`, or `SUMMARY`. The proof is a **stop test**. The content is **filled
forms**.

The design team is `architect -> designer x N -> critic`. The architect cuts the
subsystem into modules and freezes the interfaces. The designers work in parallel, one
for each module. The critic reviews the union. Rules: `reference/module-rules.md`.

## Working State

The unit of design is the **subsystem**, not the pass. One living record for each
subsystem, edited in place. No per-pass directory, no revision, no status, no change
log: the latest content of a file is its whole truth.

A change is a **delta pass** over that record. Read the record, then edit only the
sections the change touches and add only the rows it needs. Never copy a template over
the record and never regenerate a table the change does not touch. The dispatch carries
the delta, not the whole record.

```
design/subsystems/<subsystem>/
  01-interrogator/   the interrogator's sections, one file per section
  02-architect/      the architect's sections, and ARCHITECTURE.md (the module map)
  interfaces/        THE FROZEN INTERFACES - one living file for each module
    <module>.md
  modules/           one record for each module
    <module>/        DESIGN.md (wiring, seam, test map) + SKELETON.md (the contracts)
                     + decisions.md
  04-critic/         the critic's sections
  SKELETON.md        GENERATED by `swarm.genRecord` from the module skeletons, with the
                     critic's brief from `04-critic/3-skeleton.md`; the coder and the
                     refactorer read this, not the sections
  model.json         the topology for the visual view (the source of truth for the diagram)
  model.html         generated by umlview `render.py`; reload with F5
```

A new subsystem is one new directory. A change to a subsystem is an edit to its record,
never a new directory.

The role directories are numbered: `01-interrogator/`, `02-architect/`,
`04-critic/`. A designer writes its module in `modules/<module>/`,
passed by `#WORK`. `harness.py init-work <role> --subsystem <subsystem>` writes a
role's empty forms for a new record. `harness.py check <role> --subsystem <subsystem>`
lints them. For a designer, pass
`--work design/subsystems/<subsystem>/modules/<module>`.

The interrogator also owns the **requirement document** (`docs/specs/NN-<subsystem>.md`
- refine a draft or create it). The record wins if the two disagree. Write design in the
design workplace (`swarm-forge-lite/design/`), never in the repo. Only the requirement
document is authored in the repo.

Each role fills the section files of its own work directory. There is no separate
"record": the role sections **are** the record. The architect writes `model.json`. The
critic reads the union and writes the subsystem `SKELETON.md`. If the model and the
record disagree, the record wins and the model is generated again.

## The Parallel Split

A module is a unit that one designer can design alone. The **frozen interface** is the
overlap between two modules, the only thing two designers share.

- **Owns** - the paths a module writes. Two modules never share a path.
- **Freeze** - one living file for each module at `interfaces/<module>.md`: the
  provides, the requires, the consumer list, and the shared-file note. No version.
- **Parallel** - dispatch only when the write sets are disjoint and every shared edge
  is frozen. Otherwise the orchestrator serializes the affected modules.

A designer that cannot honor a frozen interface stops with `CONFLICT`; it never edits
the frozen zone. The talk-back is below. The full rules are in
`reference/module-rules.md`.

## The Visual at Every Gate

The operator views `design/subsystems/<subsystem>/model.html` before accepting a design
section (the interrogator has no model). The model and its rules belong to
`unclebob/uml-viewer`; the design team's mapping onto it is in
`reference/model-format.md`. The viewer enforces the dependency rule only, so the DIP
check is expressed by ordering `levels` core-inner -> shell-outer, not by a finding.

## Input - The Design Dispatch

The design dispatch has the shape of `dispatch.md`: a verb-led headline, labelled
blocks, and the ask with the hard constraints last. The headline is the ask (`Frame:` /
`Architect:` / `Design:` / `Critique:`); do not repeat it in the tail. **Cite the
delta**: give the path and the section of each accepted section this phase needs. Paste
only what no file holds. There is no size limit.

```
<Verb>: <subsystem> - <one-line outcome>

#SUBSYSTEM   <subsystem>
#ROLE        <architect | designer | critic>
#MODULE      <module id - designer only>
#WORK        design/subsystems/<subsystem>/<nn>-<role>/  or  design/subsystems/<subsystem>/modules/<module>/
#LANE        <subsystem>  -  or <subsystem>.<module> for a parallel designer>
#CHANGE CLASS <module-internal | module-cut | requirement-level | new-subsystem>

#REQUEST     <the operator's ask, verbatim - the interrogator only>
#DRAFT       <docs/specs/NN-<subsystem>.md, or none - the interrogator resolves it with the operator>
<cite the draft's acceptance criteria: path:line, when a draft exists>
#DELTA       <the change this pass adds: the exact sections and rows it touches. The whole
 subsystem record already exists; the role reads it and edits only what #DELTA names.>
#ACCEPTANCE
<one observable business check per line, each as a path:line cite - its source moves with the phase; see below>
#FEATURES    <approved feature paths, or none>
<cite the approved scenario outcome lines: path:line>
#SCOPE       <cite the scope-gate answers: the exclusion rows (YAGNI) and the scale
 constraints, as path:line. The near-term use cases are in scope; every other case is
 out. A module, interface, or seam with no scope answer is a defect.>
#FROZEN
<cite the accepted upstream sections this phase needs: the path and the section. For a
 designer, cite the module map rows and the frozen interface of its module.>
#INTERFACES  <the path of each frozen interface this module touches - designer only>
<cite the interface path; the role reads it>

#ENV         <cite PROJECT.md section ENV. On a resumed session: "same ENV as the previous dispatch">
#CONVENTIONS <cite PROJECT.md section CONVENTIONS, or "none">

#STOP TEST
<cite reference/design-quality.md section <role> - the pass clauses for this chunk. The full list is the module gate>

Output: <pack>/protocol/<role>.md - exactly that block.
If a detail is missing: `ASSUMED: <...>`, or surface it as a DECISION.
```

**`#LANE` is the subsystem name.** A parallel designer uses `<subsystem>.<module>`, so
the artifacts, caches, and generated tests of two modules never collide. A serial role
uses the subsystem name alone.

**Preload the paths and the cites.** The orchestrator runs `harness.py envelope <role>
--subsystem <subsystem>` and uses the block in the dispatch, so a role never spends its
first calls to find `<pack>`, `SPECS`, `SUBSYSTEM`, or the template and reference paths.
For a designer, add `#WORK` and `#MODULE`.

**`#FROZEN` for each phase.** The interrogator has no accepted upstream: its `#FROZEN`
is the ask of the operator and the draft requirement. The architect cites the accepted
requirement rows. A designer cites the module map rows it owns and the frozen
interfaces it touches. Cite the path of every section you do not paste.

**`#DELTA` names the change.** The record is living: `#DELTA` says which sections and
rows this pass touches. The role reads the record and edits only those.

**`#STOP TEST` is last.** It cites the pass clauses of the role in
`reference/design-quality.md`. The role declares pass on the chunk clauses; the full
list is the module gate, run by `swarm.check`.

`ACCEPTANCE` is the bridge: the observable behavior that the receiving role must
provide, cited, never designed. The interrogator audits the draft's criteria (or
derives them); the specifier gets the accepted requirement rows; the architect and the
designer get one approved scenario outcome for each line.

A role continued by its `sessionID` already holds the envelope. Send the new evidence
and the one change, not the envelope again.

## Output - The Design Answer

The state lives in the files. The answer is a thin control block: the state, the
decisions, and references. It pastes no record content. Give a `path:line` in every
content-bearing field. Format it for a human reader: one field on each line, a blank
line between the field groups, and each DECISION on its own line, indented. Do not pack
two fields on one line.

```
SUBSYSTEM: <subsystem>
ROLE: <architect | designer | critic>
MODULE: <module id>                                (designer only)
STATE: settled | open | blocked
SPEC: <the requirement document path in the repo [refined | created]>   (interrogator only)
WORK: design/subsystems/<subsystem>/<work dir>/
ARCHITECTURE: design/subsystems/<subsystem>/02-architect/ARCHITECTURE.md   (architect only)
INTERFACES: design/subsystems/<subsystem>/interfaces/                       (architect only)
SKELETON: design/subsystems/<subsystem>/modules/<module>/SKELETON.md     (designer only)
SKELETON: design/subsystems/<subsystem>/SKELETON.md                         (critic only)
STOP TEST: pass | fail
DECISIONS: <n>
  D1 [<named rule>] <path:line> - <one-line question> | options: <a> | <b> | <c> | answer: <operator's>
CONFLICT: <interface path> - <the change needed> - <why>             (designer only, or "none")
FOR OTHER ROLES: <path:line - route to <role>, or "none">
OPEN RISKS: <design defaults and assumptions, or "none">
NEXT: <designer | critic | coder | operator>
```

Keep each `DECISION` to one line: the question names the `path:line` that carries the
context. In the decisions file, separate the options with ` / `, never `|`. When the
operator's own request already uses `Dn`, prefix the decision id with the role tag
(`ARCH-D1`, `DES-D1`, `CRT-D1`), so the ids do not collide.

`STATE: settled` = the stop test passes and every DECISION carries the operator's
answer. `open` = a decision was surfaced and is unanswered. **A new DECISION makes
`settled` illegal: return `STATE: open`.** `blocked` = a frozen fact is missing,
contradictory, or needs a change: report `CONFLICT`. Each DECISION names the rule that
forces it.

## The Talk-Back

A designer that cannot honor a frozen interface returns `STATE: blocked` with
`CONFLICT`. It never edits the frozen zone. The orchestrator routes the CONFLICT to the
architect, which answers one of three ways:

- **AMEND** - edit `interfaces/<module>.md` in place; the orchestrator re-dispatches
  every consumer named in the file.
- **REJECT** - give the reason; the designer conforms.
- **REASSIGN** - move a path from one `Owns` column to another; the orchestrator
  updates `ARCHITECTURE.md`.

The consumer list bounds the re-dispatch: only the named consumers run again.

## Cross the Modules

- **In (requirement):** the operator states an ambiguous ask, with a draft when one
  exists. The interrogator resolves the requirement document first, frames the ask,
  makes it measurable, tables its behavior, and discharges what nobody stated.
  `REQUEST` is the ask verbatim. The draft is an input, never an authority.
- **Across (acceptance):** the specifier examines the settled record as a second party
  and derives one Gherkin scenario for each requirement. A defect routes back.
- **Across (architecture):** the architect cuts the subsystem into modules and freezes
  the interfaces, from the accepted requirement record. It returns the module map and
  the frozen interfaces. An uncertain split is a DECISION.
- **Across (modules):** the designers design one module each, in parallel. A designer
  that cannot honor a frozen interface returns a ONE-LINE `CONFLICT` request: the
  `path:line`, the new line, and the why. The architect answers one line - `AMEND`,
  `REJECT` or `REASSIGN` - and re-runs no design. A disagreement the checker can
  settle is fixed by the tool, never by two roles.
- **Out (design):** the critic reads the union and writes the subsystem `SKELETON.md`.
  A defect routes a `[REVISION REQUEST]` to the owning designer. The critic settles the
  skeleton at the gate.
- **Out (build):** the accepted `SKELETON.md` is the whole dispatch of the coder: the
  name of one method, its contract, and its responsibility sentence. If the coder needs
  more, fix the contract. Do not pad the dispatch.

## Edit the Record

- **Read before you write.** The section files already hold the accepted record. Read
  them, then change or add only the rows and sections this change needs. Never copy a
  template over the record and never regenerate a table the change does not touch. A
  new subsystem is the only case that starts from the empty forms.
- Edit in place, and add every row and section the work needs. Write no bookkeeping: no
  version number, no status flag, no "changed" note, no change log. The latest content
  is its whole truth.
- If a section needs another role, name it in `FOR OTHER ROLES` and set `NEXT` to that
  role.
- **Module-internal change:** run the designer for that module again.
- **Module-cut change:** a module cut, an `Owns` move, or a frozen interface change is
  not contained. Run the architect again, then every affected designer. Do not pretend
  the edit was contained.
- **Requirement-level change:** a GOAL, CONSTRAINTS, REQUIREMENTS, or table change is
  not contained. Run the interrogator again, then the specifier, the architect, and
  every affected designer.
